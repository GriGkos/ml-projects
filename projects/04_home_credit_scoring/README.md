# Кредитный скоринг: Home Credit Default Risk

Учебный ML-проект по данным соревнования [Home Credit Default Risk](https://www.kaggle.com/competitions/home-credit-default-risk/overview).

Задача проекта — предсказать вероятность того, что у клиента возникнут проблемы с погашением кредита, и отдельно проверить, насколько подробная кредитная и платёжная история улучшает скоринг по сравнению с моделью, которая видит только текущую заявку.

Работа построена как последовательное исследование: сначала изучается основная анкета и делаются простые baseline-модели, затем подключаются дополнительные таблицы с историей клиента, после чего сравниваются LightGBM, CatBoost и MLP. Все основные результаты оцениваются через 5-fold out-of-fold валидацию на одной и той же схеме разбиения.

Основная метрика — **ROC-AUC**, совпадающая с метрикой соревнования. Из-за сильного дисбаланса классов дополнительно рассматриваются **PR-AUC** и **Brier score**.

## Текущий результат

В текущем запуске основной части эксперимента лучшей самостоятельной моделью стал **CatBoost на полной матрице признаков**.

| Показатель | Значение |
| --- | ---: |
| OOF ROC-AUC, 5 фолдов | **0.79312** |

| OOF Brier score | **0.06548** |

Файл, использованный для отправки:


Название файла осталось от раннего эксперимента с ансамблями. По итогам OOF-сравнения основной интерпретируемой моделью оставлен CatBoost.

### Небольшой blend

После обучения основных моделей были проверены несколько простых комбинаций OOF-прогнозов. Лучшей из них на текущем прогоне оказалась смесь:

```text

```

Она дала:

```text

```

Это всего на `+0.00089` выше CatBoost. Такой прирост есть, но он небольшой и получен после просмотра OOF-результатов, поэтому в работе blend рассматривается именно как дополнительный эксперимент, а не как отдельная новая финальная модель.

# 1. Постановка задачи

В `application_train.csv` каждая строка соответствует одной текущей кредитной заявке. Целевая переменная `TARGET=1` означает, что у клиента возникли проблемы с погашением кредита, а `TARGET=0` — что таких проблем не зафиксировано.

В train находится **307 511 заявок**, при этом положительный класс занимает только около **8.07%** выборки.

Это важно для выбора метрик. Простая accuracy здесь мало что говорит о качестве: модель, которая почти всегда прогнозирует `TARGET=0`, могла бы получить высокую accuracy только за счёт сильного дисбаланса, но практически не помогала бы находить рискованных клиентов.

Поэтому основная задача формулируется как задача **ранжирования риска**: модель должна присвоить более высокий score тем клиентам, у которых вероятность дефолта выше.

Для этого используются вероятностные прогнозы, а основная метрика — ROC-AUC.

---

# 2. Почему сравниваются две постановки

Одна из центральных идей проекта — отделить информацию из **текущей заявки** от информации из **подробной истории клиента**.

Сначала модель получает только признаки из основной таблицы `application_train.csv`:

- демографию;
- доход;
- параметры кредита;
- сведения о занятости;
- имущество;
- внешние скоринговые признаки `EXT_SOURCE_*`;
- признаки, созданные непосредственно из анкеты.

После этого к тем же объектам добавляются агрегаты из:

- `bureau.csv`;
- `bureau_balance.csv`;
- `previous_application.csv`;
- `POS_CASH_balance.csv`;
- `installments_payments.csv`;
- `credit_card_balance.csv`.

Так можно количественно ответить на вопрос: насколько подробная информация о прошлых кредитах и платежах улучшает скоринг по сравнению с одной текущей заявкой.

Есть одно ограничение этой интерпретации: `EXT_SOURCE_1/2/3` уже находятся в основной таблице и представляют внешние скоринговые признаки. Поэтому baseline по `application_train` нельзя считать сценарием абсолютного отсутствия любой кредитной информации. В проекте он трактуется как **модель без подробных исторических таблиц Home Credit**.

# 3. Исходные данные

Исходные CSV соревнования не хранятся в репозитории и должны быть размещены в:

```text
data/raw/
```

Используются следующие таблицы.

| Таблица | Содержание | Роль в проекте |
| --- | --- | --- |
| `application_train.csv` | Основная заявка и `TARGET` | Train и признаки текущей заявки |
| `application_test.csv` | Те же признаки без `TARGET` | Kaggle test |
| `bureau.csv` | Кредиты клиента в других финансовых организациях | Долг, кредитная нагрузка, просрочки, активные кредиты |
| `bureau_balance.csv` | Помесячное состояние кредитов из bureau | История статусов кредитов |
| `previous_application.csv` | Предыдущие заявки клиента в Home Credit | Решения по заявкам, суммы, условия |
| `POS_CASH_balance.csv` | История POS/cash-кредитов | Остаток платежей и просрочки |
| `installments_payments.csv` | Плановые и фактические платежи | Задержки, недоплаты, качество обслуживания долга |
| `credit_card_balance.csv` | История кредитных карт | Баланс, лимит, платежи, использование кредита |

Исторические таблицы находятся на более детальном уровне, чем основная заявка: один `SK_ID_CURR` может встречаться десятки или сотни раз.

Поэтому их нельзя напрямую присоединить к `application_train`. Сначала каждая таблица агрегируется до уровня:

```text
1 строка = 1 SK_ID_CURR
```

и только затем объединяется с основной матрицей.

# 4. EDA

## 4.1. Размер и баланс классов

На первом шаге проверяются:

- число строк и столбцов train/test;
- уникальность `SK_ID_CURR`;
- совпадение схем train/test;
- распределение `TARGET`;
- типы признаков;
- технические и явно аномальные значения.

Основной вывод на этом этапе — сильный дисбаланс:

```text
TARGET=1 ≈ 8.07%
TARGET=0 ≈ 91.93%
```

Из-за этого в дальнейшем основной упор сделан на ROC-AUC и PR-AUC.

## 4.2. Пропуски

В Home Credit большое количество признаков имеет пропуски. Они не удаляются автоматически по одной только доле missing values.

Отсутствие значения может быть информативным само по себе: у клиента может отсутствовать один из внешних скорингов, соответствующий тип кредитной истории или отдельные сведения могут быть неприменимы.

Для MLP и линейной модели пропуски обрабатываются явно через импутацию. Деревья и бустинги используют подготовленную матрицу с сохранённой информацией о missing values.

## 4.3. Техническое значение DAYS_EMPLOYED

В данных встречается:

```text
DAYS_EMPLOYED = 365243
```

Таких строк в train около **55 тысяч**.

Это значение не интерпретируется как реальный трудовой стаж. В feature engineering оно заменяется на `NaN`, а факт наличия специального значения сохраняется отдельным бинарным признаком.

## 4.4. Выбросы

Правдоподобные большие значения дохода, кредита или аннуитета не удаляются автоматически.

Для финансовых величин длинный хвост распределения естественен. Вместо жёсткого отсечения используются исходные значения, логарифмические представления и относительные финансовые показатели.

## 4.5. Категориальные признаки

Для категориальных переменных исследуются наиболее частые значения, размеры групп и доля дефолтов внутри групп.

Для простых baseline-моделей категории кодируются one-hot encoding. CatBoost получает категориальные признаки в более естественной для него форме.

## 4.6. Корреляции

Для набора интерпретируемых числовых признаков строится корреляционная матрица Spearman. В неё входят возраст, стаж, доход, сумма кредита, аннуитет, отношение кредита к доходу, `EXT_SOURCE_1/2/3` и `TARGET`.

Spearman выбран вместо Pearson, потому что часть финансовых признаков имеет длинные хвосты, а связь с риском не обязана быть строго линейной.

# 5. Feature engineering

После EDA строится единая матрица признаков. В текущей версии после объединения источников получается около:

```text
307 511 строк
1 476 признаков
16 категориальных признаков
```

Большое число признаков связано не только с исходными колонками, но и с агрегированием исторических таблиц: для одного исходного показателя могут появляться `mean`, `min`, `max`, `sum`, `var`, количество записей и отдельные временные срезы.

## 5.1. Признаки текущей заявки

Из `application_train/application_test` добавляются:

- возраст, трудовой стаж и другие временные характеристики;
- кредит / доход;
- аннуитет / доход;
- аннуитет / кредит;
- кредит на одного члена семьи;
- доход на одного члена семьи;
- доход на ребёнка;
- агрегаты `EXT_SOURCE_1/2/3`: среднее, минимум, максимум, разброс и количество доступных источников;
- суммарные флаги документов, контактов и региональных несоответствий;
- индикатор аномального `DAYS_EMPLOYED`.

Смысл финансовых отношений — перейти от абсолютных сумм к долговой нагрузке клиента.

## 5.2. Bureau

Из `bureau.csv` строятся признаки по кредитам клиента в других финансовых организациях:

- количество кредитов;
- суммы кредитов;
- текущий долг;
- просроченная задолженность;
- средние, минимальные, максимальные и суммарные значения;
- активные и закрытые кредиты;
- наличие просрочки;
- использование доступного кредита;
- отношение долга к исходной сумме кредита;
- агрегаты по недавней истории.

Отдельно используются временные срезы примерно за последние 365 и 730 дней.

## 5.3. Bureau balance

`bureau_balance.csv` содержит помесячные состояния кредитов из bureau. Данные сначала связываются с `SK_ID_BUREAU`, затем агрегируются до клиента, чтобы сохранить информацию о динамике статусов кредита.

## 5.4. Previous applications

Из `previous_application.csv` используются:

- число прошлых заявок;
- суммы прошлых заявок;
- реально выданные суммы;
- отношения запрошенного и одобренного кредита;
- решения по заявкам;
- признаки отказов;
- временные показатели;
- характеристики недавних заявок.

## 5.5. POS/CASH

Для `POS_CASH_balance.csv` агрегируются количество наблюдений, оставшееся число платежей, текущие и максимальные просрочки, признаки наличия просрочки и показатели последних месяцев.

## 5.6. Installments payments

Для платежей рассчитываются:

- плановая сумма;
- фактически внесённая сумма;
- абсолютная недоплата;
- отношение фактического платежа к начисленному;
- задержка платежа в днях;
- факт просрочки;
- величина просрочки;
- статистики своевременности.

Отдельно рассчитывается срез по более недавним платежам примерно за последний год.

## 5.7. Credit card balance

Для кредитных карт используются текущий баланс, кредитный лимит, использование лимита, суммы снятий и платежей, отношения баланса и платежей к лимиту или долгу, а также просрочки и недавние агрегаты.

# 6. Валидация

Все основные модели сравниваются на одинаковой схеме:

```python
StratifiedKFold(
    n_splits=5,
    shuffle=True,
    random_state=2026
)
```

Для каждого объекта train получается out-of-fold prediction — прогноз модели, которая не обучалась на этом объекте. Итоговый ROC-AUC считается по полному вектору OOF-прогнозов.

Это позволяет честно сравнивать модели, строить ROC/PR-кривые, анализировать ошибки, выбирать диагностический threshold и проверять простые ансамбли.

## 6.1. Early stopping

Для LightGBM, CatBoost и MLP внутри внешнего train-фолда дополнительно выделяется небольшой стратифицированный holdout.

Схема:

```text
outer train
├── fit subset
└── early-stopping subset

outer validation
└── только OOF-оценка
```

Внешний validation-фолд не используется для выбора числа итераций.

# 7. Baseline-модели

Исследование начинается с простых моделей, чтобы понять, насколько сложные алгоритмы действительно улучшают решение.

## 7.1. Логистическая регрессия

Для числовых признаков используются median imputation, missing indicators и `StandardScaler`. Категории проходят через заполнение и `OneHotEncoder(handle_unknown='ignore')`.

Модель:

```text
LogisticRegression
C = 0.1
solver = saga
class_weight = balanced
```

Результат:

```text
OOF ROC-AUC = 0.75126
PR-AUC      = 0.23164
```

Это содержательный baseline, но линейная модель ограничена в сложных взаимодействиях между доходом, кредитной нагрузкой, внешними score и историей.

## 7.2. Одиночное дерево

Вторая простая модель — неглубокий `DecisionTreeClassifier` с ограничением размера листьев и `class_weight='balanced'`.

Результат:

```text
OOF ROC-AUC = 0.72776
PR-AUC      = 0.20338
```

Одно дерево оказалось слабее логистической регрессии, поэтому дальше используется ансамблирование деревьев.

# 9. LightGBM на полной истории

После подключения всех исторических таблиц размер матрицы вырастает примерно до 1.5 тысячи признаков.

Для LightGBM проводится подбор гиперпараметров через **Optuna**.

В текущем запуске:

```text
40 trials
≈ 119.5 минут
```

Лучшее среднее значение на этапе оптимизации:

```text
CV ROC-AUC = 0.79004
```

Найденные параметры:

```python
{
    "learning_rate": 0.01651876157664554,
    "num_leaves": 91,
    "max_depth": 9,
    "min_child_samples": 67,
    "subsample": 0.6475586232337888,
    "colsample_bytree": 0.846606826393402,
    "reg_alpha": 9.82451703598376,
    "reg_lambda": 5.359748178723411,
}
```

На текущем сохранённом OOF-прогоне LightGBM получил:

```text
ROC-AUC = 0.78856
PR-AUC  = 0.28161
Brier   = 0.06582
```

По сравнению с LightGBM только на анкете:

```text
0.78856 - 0.76706 = +0.02150 ROC-AUC
```

То есть подключение истории клиента дало один из самых заметных приростов во всём проекте.

> **Примечание.** После проверки финальной конфигурации LightGBM его 5-fold прогон будет повторён, чтобы параметры финального обучения полностью совпадали с конфигурацией, использованной при Optuna. Поэтому это значение будет ещё раз обновлено после следующего запуска.

# 10. CatBoost

После LightGBM проверяется CatBoost как альтернативный boosting для большой смешанной табличной матрицы.

Основные параметры:

```text
iterations = 12 000
learning_rate = 0.025
depth = 8
l2_leaf_reg = 8
loss = Logloss
eval_metric = AUC
task_type = GPU
early_stopping_rounds = 500
```

Число реально использованных итераций определяется отдельно на каждом фолде.

| Fold | Best iteration | ROC-AUC | PR-AUC | Brier |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 5 514 | 0.79278 | 0.28662 | 0.06560 |
| 2 | 5 471 | 0.79154 | 0.28979 | 0.06551 |
| 3 | 7 674 | 0.79370 | 0.28636 | 0.06558 |
| 4 | 3 709 | 0.79406 | 0.28943 | 0.06546 |
| 5 | 5 194 | 0.79384 | 0.29269 | 0.06526 |

Результат достаточно стабилен: ROC-AUC между фолдами находится примерно в диапазоне `0.7915–0.7941`.

Итоговый OOF:

```text
ROC-AUC = 0.79312
PR-AUC  = 0.28863
Brier   = 0.06548
```

CatBoost стал **лучшей самостоятельной моделью** текущего эксперимента и опередил текущий LightGBM на `+0.00456 ROC-AUC`.

# 11. MLP

Нейронная сеть используется как отдельный эксперимент для сравнения boosting и fully-connected подхода на той же задаче.

Первый вариант MLP показал две проблемы: выбор по сырой дисперсии зависел от масштаба признаков, а сильное `pos_weight` заметно портило калибровку вероятностей.

После этого MLP была переработана.

## 11.1. Отбор признаков

В каждом CV-фолде отдельно:

1. берутся числовые признаки;
2. используется подвыборка до 60 000 строк fit-части;
3. считается абсолютная корреляция каждого признака с `TARGET`;
4. выбираются лучшие **400 признаков**.

Validation-объекты в отборе признаков не участвуют.

## 11.2. Предобработка

Для каждого фолда отдельно:

```text
median imputation
        ↓
missing indicators
        ↓
StandardScaler
```

## 11.3. Архитектура

```text
input
  ↓
Linear → 512
BatchNorm
ReLU
Dropout(0.30)
  ↓
Linear → 256
BatchNorm
ReLU
Dropout(0.30)
  ↓
Linear → 128
BatchNorm
ReLU
Dropout(0.15)
  ↓
Linear → 1
```

Используются Dropout, BatchNorm, weight decay и early stopping.

## 11.4. Обучение

```text
loss: BCEWithLogitsLoss
optimizer: AdamW
learning_rate: 8e-4
weight_decay: 2e-4
batch_size: 4096
max_epochs: 80
scheduler: ReduceLROnPlateau
```

Сильное class weighting в финальной версии не используется.

MLP уступила boosting, но после изменения loss стала значительно лучше откалибрована.

# 12. Итоговое сравнение моделей

Все числа рассчитаны на одной 5-fold OOF-схеме.

| Модель | ROC-AUC | PR-AUC | Brier score | Время 5-fold, сек. |
| --- | ---: | ---: | ---: | ---: |
| **CatBoost — анкета + история** | **0.79312** | **0.28863** | **0.06548** | 1 145.4 |
| LightGBM — анкета + история | 0.78856 | 0.28161 | 0.06582 | 267.0 |
| MLP — анкета + история | 0.76766 | 0.25036 | 0.06737 | 276.6 |
| LightGBM — только анкета | 0.76706 | 0.25222 | 0.06734 | 39.1 |
| Логистическая регрессия | 0.75126 | 0.23164 | 0.20195 | 635.0 |
| Одиночное дерево | 0.72776 | 0.20338 | 0.20829 | 55.6 |

Время LightGBM в таблице не включает 40 trials Optuna.

## 12.1. Главные выводы

**История клиента действительно полезна.** На одной и той же модели LightGBM добавление истории увеличивает ROC-AUC примерно на `+0.0215`.

**Бустинги значительно лучше простых моделей.** CatBoost получает `0.79312` против `0.75126` у логистической регрессии.

**Одно дерево слишком слабое.** Основной эффект tree-based подхода появляется после ансамблирования большого числа деревьев.

**CatBoost лучше текущего LightGBM.** Он показывает более высокий ROC-AUC, PR-AUC и немного лучший Brier score.

**MLP не смогла победить boosting.** На данном представлении табличных данных fully-connected сеть хуже использует сложные взаимодействия в агрегированной истории.

# 16. Интерпретация, ошибки, fairness и ablation

В ноутбуке предусмотрены следующие диагностические блоки.

## 16.1. FP/FN

Клиенты делятся на TP, TN, FP и FN. Для групп сравниваются средний score, возраст, отношение кредита к доходу и агрегированный `EXT_SOURCE`.

Особый интерес представляют FP и FN: первые показывают хороших клиентов, которых модель считает рискованными, вторые — дефолты, которые модель недооценивает.

## 16.2. CatBoost feature importance и SHAP

Для финального CatBoost строятся встроенные feature importance и SHAP values на случайной подвыборке train.

SHAP используется как интерпретация поведения модели, а не как доказательство причинной связи.

## 16.3. Fairness

Сравнение выполняется по `CODE_GENDER` и возрастным группам. Для групп рассчитываются размер, base rate дефолта, positive prediction rate, TPR, FPR, FNR, ROC-AUC и PR-AUC при одном глобальном threshold.

Различия между группами являются диагностическим результатом и сами по себе не доказывают дискриминацию.

## 16.4. Ablation study

Для оценки вклада крупных источников из полной матрицы по очереди исключаются:

1. признаки bureau;
2. признаки previous applications;
3. платёжная история: POS, installments и credit card.

Каждый вариант повторно оценивается через 5-fold LightGBM.

Окончательные численные результаты всех четырёх блоков будут добавлены после следующего полного прогона ноутбука.

# 18. Что оказалось наиболее полезным

1. **Подробная кредитная история дала крупный прирост.** Для LightGBM разница между анкетой и полной матрицей составила около `+0.0215 ROC-AUC`.

# 21. Ограничения

**CV случайная, а не временная.** Для реальной кредитной модели дополнительно нужна валидация на более новых когортах.

**Это конкурсные данные.** Проект не является готовой банковской risk-моделью. Для production потребовались бы мониторинг drift, бизнес-функция стоимости ошибок, калибровка, стабильность, риск-политика, юридический и fairness-аудит.

**`EXT_SOURCE_*` уже несут внешнюю скоринговую информацию.** Поэтому вариант «только анкета» не равен полному отсутствию любой внешней кредитной истории.

**OOF является основной локальной оценкой.** Public/private leaderboard используется как дополнительная внешняя проверка, а не как validation set для ручного подбора.
