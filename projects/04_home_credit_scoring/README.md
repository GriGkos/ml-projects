# Кредитный скоринг: Home Credit Default Risk

Учебный ML-проект по данным соревнования [Home Credit Default Risk](https://www.kaggle.com/competitions/home-credit-default-risk/overview).

Задача проекта — предсказать вероятность того, что у клиента возникнут проблемы с погашением кредита, и отдельно проверить, насколько подробная кредитная и платёжная история улучшает скоринг по сравнению с моделью, которая видит только текущую заявку.

Работа построена как последовательное исследование: сначала изучается основная анкета и строятся простые baseline-модели, затем подключаются дополнительные таблицы с историей клиента, после чего сравниваются LightGBM, CatBoost и MLP. Все основные результаты оцениваются через 5-fold out-of-fold валидацию на одной и той же схеме разбиения.

Основная метрика — **ROC-AUC**, совпадающая с метрикой соревнования. Из-за сильного дисбаланса классов дополнительно рассматриваются **PR-AUC** и **Brier score**.

---

## Финальный результат

Лучшей самостоятельной моделью стал **CatBoost на полной матрице признаков**.

| Показатель | Значение |
| --- | ---: |
| OOF ROC-AUC, 5 фолдов | **0.79405** |
| OOF PR-AUC | **0.28957** |
| OOF Brier score | **0.06541** |
| Private leaderboard Kaggle | **0.79510** |
| Public leaderboard Kaggle | **0.79479** |

Локальная OOF-оценка и результат на скрытом leaderboard находятся очень близко:

```text
OOF ROC-AUC      0.79405
Public Kaggle    0.79479
Private Kaggle   0.79510
```

Такое совпадение говорит о том, что выбранная схема валидации достаточно хорошо оценивает качество модели на невидимых данных.

Результат находится примерно в верхних 10% решений соревнования.

Финальный файл для отправки:

```text
submissions/submission_catboost_v2.csv
```

## Что дало основной прирост

Проект специально построен так, чтобы можно было отделить эффект усложнения модели от эффекта дополнительных данных.

| Этап | OOF ROC-AUC | Прирост к предыдущему |
| --- | ---: | ---: |
| Логистическая регрессия — только заявка | 0.75141 | — |
| LightGBM — только заявка | 0.76724 | **+0.01583** |
| LightGBM — заявка + история | 0.78538 | **+0.01814** |
| CatBoost — заявка + история | **0.79405** | **+0.00867** |
| Cross-fitted CatBoost + LightGBM | 0.79440 | +0.00035 |

Из таблицы видно три основных источника улучшения:

1. переход от линейной модели к ансамблю деревьев дал около `+0.0158 ROC-AUC`;
2. подробная кредитная и платёжная история добавила LightGBM ещё `+0.0181`;
3. CatBoost лучше использовал большую разнородную матрицу и добавил ещё `+0.0087`.

Ансамбль моделей улучшил OOF всего на `+0.00035`. Этот прирост был проверен отдельно через второй уровень cross-validation и не подтвердился на Kaggle, поэтому финальной моделью остался CatBoost.

## Проверка ансамбля

В ранней версии работы простые веса ансамбля проверялись на тех же OOF-прогнозах, по которым затем измерялся результат. Такой подход немного оптимистичен, поэтому в финальной версии используется отдельный второй уровень 5-fold CV.

На каждом meta-fold:

1. вес LightGBM выбирается только на 4/5 OOF-прогнозов;
2. выбранный вес проверяется на оставшейся 1/5;
3. после пяти фолдов собирается отдельный cross-fitted OOF ансамбля.

Полученные веса LightGBM:

```text
0.20
0.20
0.15
0.20
0.15
```

Средний вес для test:

```text
CatBoost  0.82
LightGBM  0.18
```

Итог:

```text
CatBoost OOF              0.79405
Cross-fitted blend OOF    0.79440
Прирост                  +0.00035
```

Для внешней проверки на Kaggle были отправлены обе версии:

| Submission | Public | Private |
| --- | ---: | ---: |
| **CatBoost v2** | **0.79479** | **0.79510** |
| Cross-fitted blend | 0.79466 | 0.79473 |

На leaderboard небольшое преимущество blend не подтвердилось. Поэтому CatBoost оставлен финальной моделью, а ансамбль — как дополнительный корректно проверенный эксперимент.

# 1. Постановка задачи

В `application_train.csv` каждая строка соответствует одной текущей кредитной заявке. Целевая переменная `TARGET=1` означает, что у клиента возникли проблемы с погашением кредита, а `TARGET=0` — что таких проблем не зафиксировано.

В train находится **307 511 заявок**, при этом положительный класс занимает только около **8.07%** выборки.

Это важно для выбора метрик. Простая accuracy здесь мало что говорит о качестве: модель, которая почти всегда прогнозирует `TARGET=0`, могла бы получить высокую accuracy только за счёт сильного дисбаланса, но практически не помогала бы находить рискованных клиентов.

Поэтому основная задача формулируется как задача **ранжирования риска**: модель должна присвоить более высокий score тем клиентам, у которых вероятность дефолта выше.

Основной метрикой используется ROC-AUC. Дополнительно считаются:

- PR-AUC — чтобы отдельно контролировать качество на редком положительном классе;
- Brier score — чтобы оценивать качество вероятностных предсказаний.

---

# 2. Почему сравниваются две постановки

Одна из центральных идей проекта — отделить информацию из **текущей заявки** от информации из **подробной истории клиента**.

Сначала модель получает только признаки из основной таблицы `application_train.csv`:

- демографию;
- доход;
- параметры кредита;
- сведения о занятости;
- имущество;
- внешние скоринговые признаки `EXT_SOURCE_*`;
- признаки, созданные непосредственно из анкеты.

После этого к тем же объектам добавляются агрегаты из:

- `bureau.csv`;
- `bureau_balance.csv`;
- `previous_application.csv`;
- `POS_CASH_balance.csv`;
- `installments_payments.csv`;
- `credit_card_balance.csv`.

Так можно количественно ответить на вопрос: насколько подробная информация о прошлых кредитах и платежах улучшает скоринг по сравнению с одной текущей заявкой.

Есть одно ограничение этой интерпретации: `EXT_SOURCE_1/2/3` уже находятся в основной таблице и представляют внешние скоринговые признаки. Поэтому baseline по `application_train` нельзя считать сценарием абсолютного отсутствия любой кредитной информации. В проекте он трактуется как **модель без подробных исторических таблиц Home Credit**.

# 3. Исходные данные

Исходные CSV соревнования не хранятся в репозитории и должны быть размещены в:

```text
data/raw/
```

Используются следующие таблицы.

| Таблица | Содержание | Роль в проекте |
| --- | --- | --- |
| `application_train.csv` | Основная заявка и `TARGET` | Train и признаки текущей заявки |
| `application_test.csv` | Те же признаки без `TARGET` | Kaggle test |
| `bureau.csv` | Кредиты клиента в других финансовых организациях | Долг, кредитная нагрузка, просрочки, активные кредиты |
| `bureau_balance.csv` | Помесячное состояние кредитов из bureau | История статусов кредитов |
| `previous_application.csv` | Предыдущие заявки клиента в Home Credit | Решения по заявкам, суммы, условия |
| `POS_CASH_balance.csv` | История POS/cash-кредитов | Остаток платежей и просрочки |
| `installments_payments.csv` | Плановые и фактические платежи | Задержки, недоплаты, качество обслуживания долга |
| `credit_card_balance.csv` | История кредитных карт | Баланс, лимит, платежи, использование кредита |

Исторические таблицы находятся на более детальном уровне, чем основная заявка: один `SK_ID_CURR` может встречаться десятки или сотни раз.

Поэтому их нельзя напрямую присоединить к `application_train`. Сначала каждая таблица агрегируется до уровня:

```text
1 строка = 1 SK_ID_CURR
```

и только затем объединяется с основной матрицей.

Для всех основных merge используется `validate='one_to_one'`. После сборки полной матрицы число строк остаётся равным `307 511`, то есть исходная гранулярность заявки не нарушается.

# 4. EDA

## 4.1. Размер и баланс классов

На первом шаге проверяются:

- число строк и столбцов train/test;
- уникальность `SK_ID_CURR`;
- совпадение схем train/test;
- распределение `TARGET`;
- типы признаков;
- технические и явно аномальные значения.

Основной результат — сильный дисбаланс:

```text
TARGET=1 ≈ 8.07%
TARGET=0 ≈ 91.93%
```

Из-за этого в дальнейшем основной упор сделан на ROC-AUC и PR-AUC, а все CV-разбиения выполняются со стратификацией.

## 4.2. Пропуски

В Home Credit большое количество признаков имеет пропуски. Они не удаляются автоматически по одной только доле missing values.

Отсутствие значения может быть информативным само по себе:

- у клиента может отсутствовать один из внешних скорингов;
- может не быть определённого типа кредитной истории;
- некоторые сведения неприменимы для конкретного клиента;
- разные дополнительные источники покрывают разную долю заявителей.

Для MLP и линейной модели пропуски обрабатываются явно через импутацию. CatBoost и LightGBM работают с подготовленной матрицей с сохранённой информацией о missing values.

## 4.3. Техническое значение DAYS_EMPLOYED

В данных встречается:

```text
DAYS_EMPLOYED = 365243
```

Таких строк в train около **55 тысяч**.

Это значение не интерпретируется как реальный трудовой стаж. В feature engineering:

1. значение заменяется на `NaN`;
2. факт наличия специального значения сохраняется отдельным бинарным признаком.

## 4.4. Выбросы

Правдоподобные большие значения дохода, кредита или аннуитета не удаляются автоматически.

Для финансовых величин длинный хвост распределения естественен. Вместо жёсткого отсечения используются:

- исходные значения;
- логарифмические представления;
- относительные финансовые показатели.

## 4.5. Категориальные признаки

Для категориальных переменных исследуются наиболее частые значения, размеры групп и доля дефолтов внутри групп.

Для простых baseline-моделей категории кодируются one-hot encoding. CatBoost получает категориальные признаки в нативном виде.

## 4.6. Корреляции

Для набора интерпретируемых числовых признаков строится корреляционная матрица Spearman.

В неё входят:

- возраст;
- стаж;
- доход;
- сумма кредита;
- аннуитет;
- отношение кредита к доходу;
- `EXT_SOURCE_1/2/3`;
- `TARGET`.

Spearman выбран вместо Pearson, потому что часть финансовых признаков имеет длинные хвосты, а связь с риском не обязана быть строго линейной.

# 5. Feature engineering

После EDA строится единая матрица признаков.

Финальная версия содержит:

```text
307 511 строк
2 708 признаков
16 категориальных признаков
```

Из них:

```text
1 082 признака feature engineering v2
```

Вторая итерация feature engineering появилась после того, как первая версия эксперимента показала большой вклад кредитной истории. Поэтому основной акцент был сделан не на добавлении случайных признаков, а на более подробном описании **недавнего поведения** и **отдельных кредитных договоров**.

## 5.1. Признаки текущей заявки

Из `application_train/application_test` добавляются:

- возраст;
- трудовой стаж;
- время с регистрации;
- время с последней смены телефона;
- возраст на момент начала текущей работы;
- кредит / доход;
- аннуитет / доход;
- аннуитет / кредит;
- кредит на одного члена семьи;
- доход на одного члена семьи;
- доход на ребёнка;
- доля детей в семье;
- агрегаты `EXT_SOURCE_1/2/3`;
- суммарные флаги документов, контактов и региональных несоответствий;
- количество запросов кредитного бюро;
- индикатор аномального `DAYS_EMPLOYED`.

Дополнительно в v2 появились:

- разница между размером кредита и стоимостью товара;
- отношение этой разницы к стоимости товара;
- аннуитет / стоимость товара;
- попарные взаимодействия `EXT_SOURCE`;
- произведение всех трёх `EXT_SOURCE`;
- взаимодействия внешнего score с возрастом и кредитной нагрузкой.

Смысл относительных признаков — перейти от абсолютных сумм к более содержательной характеристике долговой нагрузки.

## 5.2. Bureau

Из `bureau.csv` строятся признаки по кредитам клиента в других финансовых организациях:

- количество кредитов;
- суммы кредитов;
- текущий долг;
- просроченная задолженность;
- кредитные лимиты;
- активные и закрытые кредиты;
- наличие просрочки;
- число продлений;
- отношение долга к исходной сумме кредита;
- отношение просрочки к долгу и кредиту;
- фактические и плановые даты завершения.

Для `bureau_balance` статусы преобразуются в признаки тяжести просрочки и факта проблемного статуса.

### Временные срезы bureau

В v2 отдельно считаются агрегаты за:

```text
180 дней
365 дней

```

Кроме того, отдельно описываются последние:

```text

```

Это позволяет модели отличать старую кредитную историю от более актуального поведения клиента.

## 5.3. Previous applications

Из `previous_application.csv` используются:

- число прошлых заявок;
- запрошенные суммы;
- реально одобренные суммы;
- аннуитет;
- стоимость товара;
- down payment;
- отношения между суммами заявки;
- approved/refused;
- временные показатели.

В v2 добавлены временные окна:

```text
180 / 365 / 730 / 1095 дней
```

и признаки последних:

```text
1 / 3 / 5 заявок
```

## 5.4. POS/CASH

Для `POS_CASH_balance.csv` используются:

- количество наблюдений;
- оставшееся число платежей;
- `SK_DPD`;
- `SK_DPD_DEF`;
- флаг просрочки;
- флаг серьёзной просрочки;
- отношение оставшихся платежей к первоначальному числу.

Временные окна:

```text

```

## 5.5. Installments payments

Для каждого платежа рассчитываются:

- плановая сумма;
- фактически внесённая сумма;
- абсолютная недоплата;
- отношение фактического платежа к начисленному;
- дни задержки;
- дни досрочной оплаты;
- факт просрочки;
- факт недоплаты.

Временные срезы:

```text

```

## 5.6. Credit card balance

Для кредитных карт используются:

- баланс;
- кредитный лимит;
- utilisation;
- суммы снятий;
- платежи;
- отношение платежа к балансу;
- использование лимита;
- просрочки;
- превышение лимита.

Временные окна:

```text
3 / 6 / 12 / 24 месяца
```

## 5.7. Двухуровневые агрегаты

Для POS, installments и credit cards используется дополнительный уровень агрегации:

```text
операции
   ↓
отдельный договор SK_ID_PREV
   ↓
профиль договора
   ↓
клиент SK_ID_CURR
```

Так сохраняется часть структуры истории, которая терялась бы при прямой агрегации миллионов операций сразу до клиента.

Например, можно отличить клиента, у которого проблемы сосредоточены в одном кредите, от клиента с систематическими просрочками по нескольким договорам.

# 6. Валидация

Все основные модели сравниваются на одинаковой схеме:

```python
StratifiedKFold(
    n_splits=5,
    shuffle=True,
    random_state=2026
)
```

Для каждого объекта train получается out-of-fold prediction — прогноз модели, которая не обучалась на этом объекте.

Итоговые ROC-AUC, PR-AUC и Brier score считаются уже по полному вектору OOF-прогнозов.

Это позволяет:

- честно сравнивать модели;
- строить ROC/PR-кривые;
- анализировать ошибки;
- выбирать диагностический threshold;
- проверять ансамбли;
- сравнивать локальный результат с Kaggle.

## 6.1. Early stopping

Для LightGBM, CatBoost и MLP внутри внешнего train-фолда дополнительно выделяется небольшой стратифицированный holdout.

Схема:

```text
outer train
├── fit subset
└── early-stopping subset

outer validation
└── только OOF-оценка
```

Внешний validation-фолд не используется для выбора числа итераций.

# 7. Baseline-модели

Исследование начинается с простых моделей, чтобы понимать, насколько сложные алгоритмы действительно улучшают решение.

## 7.1. Логистическая регрессия

Для числовых признаков используются:

- median imputation;
- missing indicators;
- `StandardScaler`.

Категории проходят через:

- заполнение;
- `OneHotEncoder(handle_unknown='ignore')`.

Модель:

```text
LogisticRegression
C = 0.1
solver = saga
class_weight = balanced
```

Результат:

```text
OOF ROC-AUC = 0.75141
PR-AUC      = 0.23143
```

Это основной линейный baseline, относительно которого дальше измеряется вклад нелинейности и кредитной истории.

## 7.2. Одиночное дерево

Вторая простая модель — неглубокий `DecisionTreeClassifier`.

Результат:

```text
OOF ROC-AUC = 0.72805
PR-AUC      = 0.20346
```

Одно дерево оказалось слабее логистической регрессии. Это показывает, что одной нелинейности недостаточно — основной эффект tree-based подхода появляется при ансамблировании деревьев.

# 8. LightGBM только по текущей заявке

Следующий этап — сильный tree-based алгоритм без подробных исторических таблиц.

Результат:

```text
OOF ROC-AUC = 0.76724
PR-AUC      = 0.25312
Brier       = 0.06731
```

Прирост относительно логистической регрессии:

```text

```

# 11. MLP

Нейронная сеть используется как отдельный эксперимент для сравнения boosting и fully-connected подхода на той же задаче.

В каждом CV-фолде:

1. берутся только числовые признаки;
2. на fit-части считается абсолютная корреляция с `TARGET`;
3. выбираются лучшие **400 признаков**;
4. выполняются median imputation и StandardScaler.

Validation-объекты не участвуют в отборе признаков.

BatchNorm
ReLU

  ↓

# 14. Что именно даёт кредитная история

Чтобы довести вывод о пользе истории до уровня отдельных источников, для CatBoost рассчитывается **group permutation importance** на внешних OOF-фолдах.

Для каждого фолда:

1. считается исходный ROC-AUC;
2. все признаки одной группы одновременно перемешиваются;
3. ROC-AUC считается повторно;
4. падение метрики показывает, насколько модель зависит от этой группы.

Для экономии памяти используется воспроизводимая стратифицированная подвыборка до 30 000 объектов из каждого validation-фолда.

## 14.1. Источники данных

| Группа | Число признаков | Среднее падение ROC-AUC |
| --- | ---: | ---: |
| Текущая заявка | 162 | **0.15414** |
| Bureau | 1160 | **0.01977** |
| Installments | 213 | **0.01701** |
| Previous applications | 679 | **0.01491** |
| POS/CASH | 187 | 0.00732 |
| Credit card | 307 | 0.00609 |

Среди дополнительных исторических таблиц наибольший сигнал дают:

1. **bureau**;
2. **installments**;
3. **previous applications**.

То есть основной дополнительный эффект истории связан с внешними кредитами, фактическим платёжным поведением и предыдущими решениями по заявкам.

## 14.2. Вклад feature engineering v2

| Группа | Число признаков | Среднее падение ROC-AUC |
| --- | ---: | ---: |
| Все новые v2-признаки | 1082 | **0.03981** |
| Недавние временные окна | 798 | **0.01630** |
| Новые взаимодействия анкеты | 9 | 0.00511 |
| Агрегаты отдельных договоров | 138 | 0.00224 |
| Последние 1/3/5 событий | 90 | 0.00197 |

Самым полезным новым направлением оказались **недавние временные окна**.

Это подтверждает гипотезу второй итерации feature engineering: недавнее поведение клиента не стоит полностью смешивать со всей многолетней историей.

Значения permutation importance нельзя складывать между собой. Группы пересекаются, а признаки внутри них коррелируют.

# 15. Интерпретация CatBoost

Для финального CatBoost используются:

- встроенный feature importance;
- SHAP values на случайной подвыборке train.

Среди наиболее заметных признаков:

- `APP__EXT_SOURCE_MEAN`;
- минимум и максимум `EXT_SOURCE`;
- отдельные `EXT_SOURCE_*`;
- возраст и взаимодействия возраста с внешними score;
- финансовые отношения;
- сумма фактических платежей installments;
- новые v2-взаимодействия `EXT_SOURCE`;
- разница между размером кредита и стоимостью товара.

SHAP используется для интерпретации поведения уже обученной модели и не рассматривается как доказательство причинной связи между признаком и дефолтом.

# 16. Рабочий порог CatBoost

Kaggle использует ROC-AUC и принимает непрерывные вероятности, поэтому threshold для submission не нужен.

Для содержательного анализа выбирается порог по максимуму F1 на OOF-прогнозах CatBoost.

Получено:

```text
threshold = 0.1499
```

| Метрика | Значение |
| --- | ---: |
| Precision | 0.2779 |
| Recall / TPR | 0.4722 |
| F1 | 0.3499 |
| FPR | 0.1078 |
| False negatives | 13 102 |
| False positives | 30 468 |

При этом пороге модель находит примерно **47% дефолтов**.

Цена такой чувствительности — заметное количество false positives.

Этот threshold является только диагностическим. В реальном кредитном продукте порог должен выбираться через стоимость FP/FN, маржинальность, риск-политику и другие бизнес-ограничения.

# 17. Анализ ошибок

Для выбранного threshold объекты делятся на:

```text
TP — дефолт правильно найден
TN — хороший клиент определён правильно
FP — хороший клиент ошибочно признан рискованным
FN — дефолт пропущен
```

Профили ошибок показывают, что false positives по внешним скорингам заметно похожи на реальные дефолты.

У false negatives агрегированный `EXT_SOURCE` выше: часть будущих дефолтов выглядит для модели относительно надёжно и поэтому остаётся ниже выбранного порога.

Это показывает, что ошибки не сводятся только к неудачно выбранному threshold — часть клиентов действительно имеет сложный для модели профиль.

# 24. Ограничения

**CV случайная, а не временная.** Для реальной кредитной модели дополнительно нужна валидация на более новых когортах.

**Это конкурсные данные.** Проект не является готовой банковской risk-моделью. Для production потребовались бы мониторинг drift, бизнес-функция стоимости ошибок, калибровка, мониторинг стабильности, риск-политика, юридический и fairness-аудит.

**`EXT_SOURCE_*` уже несут внешнюю скоринговую информацию.** Поэтому вариант «только анкета» не равен полному отсутствию любой внешней кредитной истории.

**Permutation importance не является аддитивным разложением качества.** Группы признаков пересекаются и коррелируют, поэтому падения ROC-AUC нельзя складывать.

**OOF является основной локальной оценкой.** Public/private leaderboard используется как дополнительная внешняя проверка, а не как validation set для ручного подбора.
