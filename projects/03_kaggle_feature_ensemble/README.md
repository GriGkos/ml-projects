# Прогноз лояльности клиентов: Elo Merchant Category Recommendation

Проект выполнен по данным соревнования Kaggle [Elo Merchant Category Recommendation](https://www.kaggle.com/competitions/elo-merchant-category-recommendation). Это исследование полного ML-пайплайна: от первичного анализа крупных транзакционных таблиц до генерации итогового файла для Kaggle.

Рабочий код, графики, промежуточные таблицы и результаты экспериментов находятся в [ноутбуке](notebooks/solution.ipynb). Итоговый файл для соревнования: [submission_xgboost_seed_bagging.csv](submissions/submission_xgboost_seed_bagging.csv).

## Постановка задачи

Для каждой банковской карты из тестовой выборки необходимо предсказать непрерывную целевую переменную `target`. Организаторы называют её показателем лояльности клиента, однако смысл таргета не раскрыт, а часть исходных признаков анонимизирована. Поэтому основной источник сигнала в этой задаче - не исходные признаки карты, а её поведение в транзакциях.

Задача является регрессией. В соревновании используется метрика RMSE:

```text
RMSE = sqrt(mean((y_true - y_pred)^2))
```

Меньшее значение RMSE означает более точный прогноз. Эта же метрика применялась при сравнении всех моделей и наборов признаков внутри исследования.

## Данные

Все данные доступны на странице соревнования. В репозиторий они не добавлены из-за размера и условий распространения, но ноутбук ожидает их в каталоге `data/` проекта.

| Файл | Строк | Столбцов | Роль в исследовании |
| --- | ---: | ---: | --- |
| `train.csv` | 201 917 | 6 | Карты с известным `target` |
| `test.csv` | 123 623 | 5 | Карты, для которых строится прогноз |
| `historical_transactions.csv` | 29 112 361 | 14 | История операций до контрольного периода |
| `new_merchant_transactions.csv` | 1 963 031 | 14 | Операции нового периода |
| `merchants.csv` | 334 696 | 22 | Атрибуты продавцов |
| `sample_submission.csv` | 123 623 | 2 | Формат отправляемого файла |

### Таблицы карт

`train.csv` и `test.csv` содержат идентификатор карты `card_id`, месяц первой активности `first_active_month` и три анонимизированных категориальных признака `feature_1`, `feature_2`, `feature_3`. В `train.csv` дополнительно есть `target`.

Карты уникальны в обеих выборках. В тесте есть один пропуск в `first_active_month`, поэтому пропуск не заменялся произвольным значением: для него создан отдельный индикатор. Это сохраняет информацию о том, что дата неизвестна, и не создаёт искусственную дату.

### Целевая переменная

Распределение `target` асимметрично: среднее равно `-0.394`, медиана `-0.023`, стандартное отклонение `3.850`. В данных есть небольшой отдельный хвост очень низких значений: 2 207 карт, или 1.09% обучающей выборки, имеют `target < -30`. Минимум равен `-33.219`, максимум `17.965`.

Этот сегмент важен для RMSE: несколько больших ошибок на экстремальных объектах заметно влияют на итоговую метрику. Поэтому при валидации была использована стратификация по индикатору `target < -30`, а отдельно проверялась гипотеза о специальной обработке таких наблюдений.

### Таблицы транзакций и продавцов

Обе таблицы транзакций имеют одинаковую схему: сведения об авторизации операции, сумме покупки, дате, количестве платежей в рассрочку, категории, городе, штате, подсекторе и продавце. `historical_transactions.csv` почти в 15 раз больше новой таблицы, поэтому чтение и агрегация выполняются порциями.

`merchants.csv` содержит числовые показатели активности продавца за 3, 6 и 12 месяцев, категориальные флаги, а также характеристики недавних продаж и покупок. Продавец может встречаться в таблице несколько раз, поэтому его числовой профиль усредняется по `merchant_id`. Идентификаторы и категориальные коды не усредняются как числа, чтобы не придумывать несуществующий порядок категорий.

## Первичный анализ и принятые решения

EDA показал, что исходных признаков карты немного, а понятной закономерности для экстремального сегмента только по `feature_1-3` нет. Это стало основанием строить основную модель по агрегированной транзакционной истории.

Большие транзакционные файлы не считываются целиком для исследовательских графиков. Для EDA выбираются случайные `card_id` из train и test, после чего загружаются только связанные с ними операции. Такой подход не зависит от порядка строк в файле и даёт репрезентативнее картину, чем первые `n` строк.

При итоговой обработке файлы читаются чанками. Последняя карта из чанка переносится в следующий чанк, если её операции продолжаются за границей части файла. Благодаря этому все статистики одной карты считаются по полной истории, а не по фрагменту. Это особенно важно для медианы, стандартного отклонения, числа уникальных значений и помесячной динамики.

## Инженерия признаков

Единицей моделирования выбрана карта. После агрегации все признаки имеют уровень `card_id`: одна строка матрицы соответствует одной карте, а не одной операции. Исторический и новый периоды сначала обрабатываются отдельно, затем объединяются.

### Признаки карты

Из `first_active_month` выделены год, номер месяца, квартал и порядковый индекс месяца. Отдельно создан флаг отсутствующей даты. Анонимизированные `feature_1-3` оставлены как категории, а также добавлены их попарные и тройное сочетания. Смысл этого шага - позволить модели учитывать возможные взаимодействия исходных категорий, не предполагая между ними числовой порядок.

### Временные признаки операций

Из `purchase_date` извлечены год, месяц, день недели, час и признак выходного дня. Показатель `month_lag` используется для восстановления опорного месяца карты. На его основе рассчитывается положение покупки относительно конца опорного месяца, что даёт признаки давности и временной активности.

Для каждой карты также рассчитывается помесячная динамика: число активных месяцев, среднее, разброс и максимум количества операций, суммы покупок, числа продавцов и доли авторизованных операций. Общий объём покупок сам по себе не различает стабильную и разовую активность, поэтому такие признаки добавлены отдельно.

### Категории, авторизация и рассрочка

Категориальные коды в транзакциях не усредняются. Вместо этого используются доли операций в значениях `category_2` и `category_3`, а также отдельные флаги пропусков. Для `authorized_flag` рассчитывается доля авторизованных операций.

Значения `-1` и `999` в `installments` считаются служебными, а не реальным числом платежей. Они заменяются на пропуск для числовых статистик, при этом отдельно сохраняются флаг служебного значения, доля операций без рассрочки и доля многоплатёжных операций. Такое разделение не позволяет специальным кодам исказить среднее число платежей.

### Денежные и агрегированные признаки

Для `purchase_amount` рассчитаны количество, сумма, среднее, медиана, стандартное отклонение, минимум, максимум и асимметрия. Дополнительно используются модуль суммы и знаковый логарифм `sign(x) * log(1 + |x|)`, чтобы уменьшить влияние длинного хвоста, не теряя знак операции.

Добавлены признаки разнообразия: число уникальных продавцов, категорий продавцов, подсекторов, городов и штатов. Характеристики продавца присоединяются к операции до агрегации, поэтому модель получает не только факт посещения продавца, но и средний профиль продавцов, с которыми взаимодействовала карта.

### Сравнение исторического и нового периодов

Для основных показателей строятся разности и отношения нового периода к историческому: количества операций, сумм покупок, разнообразия продавцов, средних сумм, разброса, доли авторизованных операций и помесячной активности. Эти признаки описывают изменение поведения, а не только его накопленный объём.

Также активность нормируется на возраст карты, рассчитанный по месяцу первой активности. Это защищает от ситуации, когда более старая карта выглядит активнее только потому, что наблюдалась дольше.

### Проверка вкладов групп признаков

Признаки добавлялись последовательно, и каждый следующий набор содержал предыдущий плюс одну группу: исходные признаки карты, historical-транзакции, new-транзакции, межпериодные различия, устойчивые агрегаты, помесячную динамику, нормировку на возраст и экспериментальные взаимодействия. Такой абляционный эксперимент позволил выбрать основной набор признаков по OOF RMSE, а не оставлять все признаки автоматически.

## Валидация и защита от утечек

Основная оценка строится на 5-фолдовой `StratifiedKFold` с перемешиванием и фиксированным `random_state`. Стратификация выполняется по индикатору экстремального значения `target < -30`, поэтому доля редкого сегмента остаётся сопоставимой на каждом фолде.

Для каждой модели сохраняются OOF-прогнозы, средний прогноз для теста, RMSE на каждом фолде, среднее и стандартное отклонение RMSE. Все сравниваемые модели получают одинаковые основные фолды, поэтому разница между ними не объясняется случайно удачным разбиением.

Параметры бустингов подбираются Optuna на отдельной трёхфолдовой схеме, после чего выбранная конфигурация переоценивается на основных пяти фолдах. Внутри обучения применяется early stopping. Такая последовательность отделяет поиск параметров от итогового сопоставления моделей и ограничивает число дорогих запусков на крупных таблицах.

Target encoding для сочетаний исходных категорий строится только по обучающей части каждого фолда. Для обучающей части дополнительно используются внутренние фолды. Это исключает попадание целевой переменной в признак объекта, для которого строится прогноз.

## Модели и эксперименты

### Базовые модели

`DummyRegressor` задаёт нижнюю границу качества: он предсказывает константу и получает OOF RMSE `3.850497`. `RidgeCV` на признаках карты служит простой линейной точкой отсчёта и показывает `3.842995`. Небольшая разница между ними подтверждает, что без транзакционной истории исходные признаки дают мало сигнала.

### Градиентные бустинги

Основными моделями выбраны `LightGBM`, `XGBoost` и `CatBoost`. Они умеют находить нелинейные зависимости и взаимодействия в большом наборе разнородных агрегатов. Для LightGBM и XGBoost категориальные признаки карты преобразуются через one-hot encoding; CatBoost получает исходные категориальные признаки без этого преобразования.

Для каждой модели сначала фиксируется baseline, затем Optuna подбирает скорость обучения, сложность деревьев, подвыборки строк и признаков, а также регуляризацию. После настройки XGBoost дополнительно запускается с тремя заранее выбранными `seed`. Их прогнозы усредняются: `seed` не отбираются по качеству, поэтому усреднение уменьшает случайную вариативность, а не подгоняет решение под валидацию.

### Дополнительные гипотезы

Проверены три направления улучшения:

- сглаженный target encoding для групп `feature_1-3` и месяца первой активности;
- отдельный LightGBM-классификатор для вероятности экстремального сегмента `target < -30`, который настраивается по PR-AUC из-за редкого положительного класса;
- ансамбли на OOF-прогнозах: взвешенный blend с неотрицательными весами и Ridge stacking.

Идея с отдельным классификатором была проверена потому, что экстремальные наблюдения сильно влияют на RMSE. Однако последующая замена прогноза в наиболее вероятном экстремальном сегменте ухудшила общий RMSE. Это важный результат: улучшение ошибки на хвосте не обязательно улучшает основную метрику.

## Сравнение моделей

| Модель | OOF RMSE |
| --- | ---: |
| DummyRegressor | 3.850497 |
| RidgeCV | 3.842995 |
| LightGBM с подбором параметров | 3.661095 |
| XGBoost с подбором параметров | 3.642479 |
| CatBoost с подбором параметров | 3.645502 |
| XGBoost с усреднением по трём `seed` | 3.640658 |
| Взвешенный blend | 3.640409 |
| Ridge stacking | 3.640144 |

Наименьший OOF RMSE формально показал Ridge stacking. Но его преимущество над XGBoost bagging равно только `0.000514`. Чтобы не выбирать более сложную схему по случайной малой разнице, OOF-прогнозы Ridge stacking и XGBoost bagging сравнивались парным бутстрэпом. Доверительный интервал разности включил ноль, то есть устойчивого выигрыша stacking не подтверждено.

Дополнительно настроенные LightGBM и XGBoost запускались на другом разбиении фолдов. Это проверяет, что выбор между основными одиночными моделями не держится на одной случайной разбивке.

## Финальное решение

Итоговая схема - `XGBoost` с усреднением прогнозов трёх моделей, обученных с разными заранее зафиксированными `seed`.

Выбор сделан по трём причинам:

1. Она заметно превосходит все одиночные базовые модели и улучшает настроенный XGBoost с `3.642479` до `3.640658`.
2. Сложные ансамбли дают лишь очень малое дополнительное улучшение, которое не подтвердилось бутстрэп-проверкой как устойчивое.
3. Схема проще Ridge stacking и легче воспроизводится: не требует отдельного мета-уровня и подбора его параметров.

Перед сохранением файла проверяются число строк, уникальность и порядок `card_id`, отсутствие пропусков и бесконечных значений в прогнозе. Это снижает риск технической ошибки при отправке на Kaggle.

## Что сработало и что не сработало

### Сработало

- Переход от признаков карты к агрегированной транзакционной истории дал основной прирост качества.
- Наиболее полезным оказался блок устойчивых признаков покупательской и календарной активности.
- Настройка параметров снизила OOF RMSE XGBoost с `3.655293` до `3.642479`.
- Bagging по трём `seed` дополнительно снизил OOF RMSE до `3.640658`.

### Не дало устойчивого улучшения

- Target encoding не улучшил настроенный XGBoost: `3.642831` против `3.642479`.
- Коррекция экстремального сегмента ухудшила общий RMSE, хотя локально уменьшала ошибку на хвосте.
- Взвешенный blend и Ridge stacking показали минимальное численное преимущество, но оно оказалось недостаточно устойчивым для выбора более сложной схемы.

## Воспроизведение

1. Клонировать репозиторий и перейти в ветку проекта:

   ```bash
   git clone https://github.com/GriGkos/ml-projects.git
   cd ml-projects
   git switch project/03-kaggle-feature-ensemble
   ```

2. Установить зависимости:

   ```bash
   pip install -r projects/03_kaggle_feature_ensemble/requirements.txt
   ```
